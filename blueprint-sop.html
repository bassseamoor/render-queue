Blueprint Standard Operating Procedure (SOP)

Version

1.0 — Derived from flaw assessment e0285f1b7e23cf6c

Purpose

This SOP defines the exact steps to produce a bulletproof Blueprint. A Blueprint is not a SOP. A Blueprint describes WHAT to build. This SOP describes HOW to write a Blueprint that a builder can implement without interpretation.

SOP-1: API Reality Check

Step:* List every function, method, and API referenced in the Blueprint. Procedure:*
  1. Extract all functionName(), object.method(), API.call() references
  2. For each one, check: does this exist in the target codebase?
  3. If yes: cite the file and line number
  4. If no: you have two choices —
a. Remove the reference and use an existing API b. Write the implementation inline in the Blueprint (not just the name) Fail condition:* Any referenced API that doesn't exist and isn't implemented inline. Test:* grep -r "functionName" /path/to/codebase must return a match, or the Blueprint must contain the implementation.

SOP-2: Decision Rule Mechanization

Step:* For every "decide," "choose," "select," or "determine" in the Blueprint: Procedure:*
  1. Identify the decision: what are the inputs? What are the possible outputs?
  2. Write the decision as a function: decide(inputs) → output
  3. The function must be implementable in code without human judgment
  4. If human judgment is required, that's a separate SOP step — write it as its own procedure
Fail condition:* Any decision that requires "you'll know it when you see it." Example (bad):* "Select the stronger evidence." Example (good):* "Select evidence with higher provenance score. Provenance score = (has_source ? 1 : 0) + (has_timestamp ? 1 : 0) + (corroborated ? 1 : 0). Tie → both advance."

SOP-3: Constant Justification

Step:* For every number in the Blueprint (weights, thresholds, limits, timeouts): Procedure:*
  1. List the number and where it's used
  2. For each, answer: where did this number come from?
- Measured: "We tested X and Y was optimal" (cite test) - Derived: "X follows from Y because..." (show derivation) - Tunable: "Default is X, validate by..." (provide validation procedure)
  1. If none of the above: remove the number or mark as UNDECIDED
Fail condition:* Any number without justification or validation procedure. Example (bad):* score = evidence * 10 Example (good):* score = evidence_count * 1.0 // v1: unit weight. Validate: run tournament on known-good dataset, check if champion matches expected. Tune if mismatch.

SOP-4: Mechanism Naming

Step:* Replace all metaphors with implementation names. Procedure:*
  1. Find all metaphors: "socket," "bus," "pot," "pool," "fabric," "pipeline"
  2. For each, answer: what is this in code?
- "Socket bus" → "Node.js EventEmitter" or "shared Map" or "function calls" - "Data pot" → "module-level const" or "JSON file" or "database table"
  1. Replace the metaphor with the implementation name throughout
Fail condition:* Any metaphor without a concrete implementation mapping. Test:* A junior developer reading the Blueprint should be able to npm install the right library or open the right file without asking what you meant.

SOP-5: Failure Mode Enumeration

Step:* For every component in the Blueprint: Procedure:*
  1. List the component
  2. Ask: "What happens when this fails?"
  3. Write the failure response as code or precise steps
  4. Cover at minimum: unavailable, corrupted, timeout, wrong version
Fail condition:* Any component without a failure response. Example (bad):* "If the database is unavailable, handle gracefully." Example (good):* "If db.connect() throws: retry 3x with 1s backoff. If still failing: log error, return {status:'degraded', reason:'db_unavailable'}, continue with cached data. Do not crash."

SOP-6: Test Code, Not Test Descriptions

Step:* For every "verify," "check," "ensure," or "validate": Procedure:*
  1. Write the actual test as executable code or shell command
  2. Specify the expected output
  3. Specify the fail action
Fail condition:* Any verification step without executable test code. Example (bad):* "Verify Page 0 hash matches across all seats." Example (good):* 
node -e "
const seats = require('./seats.json');
const hashes = new Set(seats.map(s => s.page0_hash));
if (hashes.size !== 1) { console.error('FAIL: multiple hashes'); process.exit(1); }
console.log('PASS: all hashes match');
"

SOP-7: Version Negotiation

Step:* Define how builders know they have the right Blueprint version. Procedure:*
  1. Every Blueprint has a version number and content hash
  2. Every implementation references the Blueprint version it was built from
  3. If Blueprint changes, specify: is this backward compatible? What breaks?
Fail condition:* No version tracking.

SOP Compliance Checklist

Before a Blueprint is accepted, it must pass all 7 SOPs:
☐ SOP-1: All APIs exist or are implemented inline
☐ SOP-2: All decisions are mechanical (no human judgment without procedure)
☐ SOP-3: All numbers justified or labeled tunable with validation
☐ SOP-4: No metaphors without implementation mapping
☐ SOP-5: Every component has failure handling
☐ SOP-6: Every verification has executable test code
☐ SOP-7: Version tracking defined
If any box is unchecked, the Blueprint is not a SOP-compliant Blueprint. It is a draft.*
