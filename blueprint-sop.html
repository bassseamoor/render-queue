§3

The five layers

Every blueprint passes through all five, in order. Tap a layer. A failed gate recurses to the failing layer — never forward.

L1Intent
L2Structure
L3Detail
L4Show
L5Verify

L1 — Intent the flower seed

Input

The raw idea, request, or problem.

Output

Promise in one breath. Stakes. The click. The SELL draft.

Gate: would a stranger want this built? If no — recurse L1.

L2 — Structure the skeleton

Input

The L1 intent.

Output

Parts list, build order, interfaces between parts. SPEC skeleton.

Gate: can every part be named and its role stated? If no — recurse L2.

L3 — Detail the buildable depth

Input

The L2 structure.

Output

Per-part build detail, per-step done-state, acceptance criteria, non-goals. Full SPEC.

Gate: could a competent builder execute from this alone, no side conversations? If no — recurse L3.

L4 — Show the rendering

Input

The L3 detail.

Output

Visual design — color with intent, dramatic layout, detail density, visible craft.

Gate: does the craft show? Does it survive the rogues gallery? If no — recurse L4.

L5 — Verify the gates

Input

The L4 rendering.

Output

Sealed funnel verdict: BUILD or FAIL.

All five must pass: SELL · SPEC · SHOW · EXEMPLAR · HONESTY. Any failure recurses to its layer. FAIL exits 1 — DO NOT SHIP.

§4

Automatic enforcement

1

No verdict, no ship

No blueprint ships without a sealed funnel verdict. The verdict is the enforcement — the procedure's output, not a person's opinion.

2

Intent-level checks

The verifier checks SELL / SPEC / SHOW at the intent level. Byte-matches and zero-errors are not verification.

3

The documented bar

The sealed verdicts archive is the quality bar — aircraft quality and beyond. New work is measured against the best documented work, automatically, every run.

§5

Discipline

A failed gate is not a suggestion. Work stops. The failing layer is re-entered. The failure gets a new check.

Never ship on a FAIL. Never waive a gate below PL authority. Never freelance outside the plan — report up. This SOP improves only by PL edit; parallel sessions do not fork it.

§6

Response discipline

Reporting is part of the SOP. Parallel workers must not create false project state through confident prose. The response may only claim the highest state independent evidence proves.

1

Name the state

Requested → funneled → implemented → verified → merged → Pulse-registered → owner-visible → deployed/live. Do not collapse them.

2

Name the destination

Say whether the result lives on a branch, render-queue/main, bassseamoor/MOOR, Project Pulse, a live deployment, or another canonical destination.

3

Name the proof

Use the actual receipt, CI result, merge SHA, Pulse registry entry, Dev Feed event, or runtime check. Worker confidence is not proof.

4

Name the gap

If deployment, Pulse visibility, owner visibility, or another requested state is not proven, say so directly. “Done” cannot hide a missing state.

Correction is append-only. If a previous response overclaimed, preserve the earlier claim, record what evidence existed at the time, and append the corrected state. Do not rewrite history.

Machine-readable response law: worker-response-sop.json. Human reference: docs/WORKER_RESPONSE_SOP.md. Dev Feed carries the observable state changes.
