THE PIPELINE

Six stages, one blueprint.

Tap a stage. The pipeline renders precision — it does not invent it. No nail-level spec, no pipeline.

P1Intake
P2Select
P3Fill
P4Gap
P5Compose
P6Verify

P1 — Intake the raw material

Collect the nail-level spec: exact hooks, exact code, exact values. Plus user notes, the click (the SELL in one breath), and ids of referenced blueprints.

Gate: no spec, no pipeline.

P2 — Select choose the components

Map each part of the spec to library components. SELL gets hero-plate / sell-grid / punch. SPEC gets one spec-plate per instruction. Contracts get data-table. Proof gets assert-list.

Every component earns its place.

P3 — Fill procedural, data-driven

Spec data into component contracts. Code goes into code-blocks verbatim. Values go into tables with their whys. No editorializing inside components — the data speaks.

P4 — Gap assembly the LLM steps in

Where no library component fits the demonstration need, the LLM assembles a new one: designs it, builds it, fills it. The new component is named, given a data contract, and enters the library — so the library grows and the LLM is needed less over time.

P5 — Compose comic-book layout

SELL opens loud. SPEC goes deep. DATA is exact. VERIFY closes with proof. Rhythm: hero, beats, reveals. Color with intent. Progress looks cool, intelligence looks exciting.

P6 — Verify against the bar

Does the craft show? Does it survive the rogues gallery? Is every instruction executable to the nail? Failures recurse to the failing stage — never a full rebuild for a local failure.

COMPONENT LIBRARY

Pick, don't invent.

Fixed data contracts. Fill the data, get the component. Library first, LLM second — always.

Verification checks, not vibes.

Exact implementation, annotated.

The gap rule:

  1. Library first — always prefer an existing component.
  2. LLM assembles only what generators cannot, and must justify why no library component fit.
  3. New components enter the library with a data contract — or they don't enter.

REFERENCES

Blueprints reference blueprints.

Blueprints cite each other by id — DL-02 cites SOP v1, this pipeline cites the Standard. In Pulse, references are deep links (dashboard?tool=<id>): the reader jumps inside the platform, never out. A blueprint's reference list is data, maintained like any other contract.

VERSIONING

Copied, not invented.

Blueprint versions ride the existing Pulse version pipeline — same pattern, less work. The page header carries the version (REV 2), the COMPS version field bumps with it, and the manifest component string records version + what changed. Builders build from a version, never "the latest." A version bump re-runs P6 Verify.
